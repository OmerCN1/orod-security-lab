# ADR 0012: Deterministic dependency remediation and recorded OSV fixtures

## Context

OSV findings were selected for automated remediation, but no patch could resolve them:
the patch provider only saw Python sources, and the residual check left OSV out so that
every run with a vulnerable dependency did not fail validation. An advisory was therefore
"selected" and never fixed. The evaluation corpus declared no pinned dependencies, so the
OSV path was not measured at all.

## Decision

A selected advisory is resolved by a deterministic pin change, not by the model.

- The OSV adapter stores on each finding the dependency it matched and the `fixed`
  events of the advisory's ECOSYSTEM and SEMVER ranges for that package. GIT ranges name
  commits and are ignored.
- An OSV finding is selected only when a fixed release above the pin exists, the pin is
  in `requirements*.txt` or `pyproject.toml` at the repository root, and the initial OSV
  lookup was complete. Lockfiles are generated by their tools and are never edited; an
  advisory pinned only in one is left for a human.
- For each advisory the target is its smallest fixed version above the pin (the range
  holding the pin ends there). A package moves to the highest of these across its
  selected advisories, compared as PEP 440 versions. Every exact `name==version` pin of
  that package in the root manifests is moved.
- The developer node sends only code findings to the patch provider, which never sees a
  manifest. The manifest diff is appended to the code patch, or is the whole patch, and
  passes the same gates. A code patch and a pin upgrade touching the same file is rejected.
- The residual check includes OSV again. The post-patch OSV lookup of the changed
  manifest is authoritative: a target the lookup still matches is unresolved, and an
  advisory the new version brings is introduced.

The corpus gains cases with pinned dependencies. Each ships an `osv.json` recorded from
the live service by `python -m evals record-osv`, and the harness replays it through the
real OSV adapter with an `httpx` transport passed to `create_app`. An unrecorded query
answers like an outage, so the lookup is incomplete and fails closed instead of reading
as "no advisories". The harness's own rescan now covers OSV as well.

## Consequences

Dependency fixes cost no model tokens and are identical across models, so the
deterministic baseline scores them too; the model's net contribution is unchanged.
Choosing the highest per-advisory fix is not a full range solver: a target inside a later
affected range of another advisory is caught by the post-patch lookup and fails
validation rather than being skipped. Transitive dependencies, version specifiers other
than `==`, pins with extras and manifests outside the repository root are not
remediated. A recording reflects OSV at the time it was made; re-recording a case can
change its expected result and must be explained like any other corpus change.
